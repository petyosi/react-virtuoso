---
title: Operators and Combinators
description: Reference for transforming and connecting nodes.
---

Combinators connect nodes; operators transform values inside a `pipe`. All are available as named exports and on the `e` namespace object. The module-scope forms register deferred wiring (applied per engine on activation); the `Engine` instance methods of the same names act immediately on one engine.

## Combinators

| Combinator                                                       | Purpose                                                                  |
| ---------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `link(source$, sink$)`                                           | Forward every emission from source to sink                               |
| `pipe(source$, ...operators)`                                    | Derive a new node by running emissions through operators                 |
| `combine(a$, b$, ...)`                                           | Node emitting `[a, b, ...]` whenever any source emits (up to 22 sources) |
| `merge(a$, b$, ...)`                                             | Node emitting each source's values individually                          |
| `sub(node$, cb)`                                                 | Subscribe; `cb(value, engine)`                                           |
| `singletonSub(node$, cb)`                                        | Exclusive subscription — replaces the previous singleton on the node     |
| `subMultiple([a$, b$], cb)`                                      | One callback over several nodes                                          |
| `changeWith(cell$, source$, (cell, value) => next)`              | Update a cell from a stream, reducer-style                               |
| `withResource(source$, resource$, (value, resource) => void)`    | Side effect pairing emissions with a resource instance                   |
| `withResources(source$, resources$, (value, resources) => void)` | Side effect pairing emissions with current resource values               |

`changeWith` is the workhorse for "action stream updates state cell":

```ts
e.changeWith(columnWidths$, resizeColumn$, (widths, { key, width }) => {
  const next = new Map(widths)
  next.set(key, width)
  return next
})
```

Return a **new** reference from the reducer — cells are distinct by reference equality, so mutating and returning the same Map emits nothing.

`withResources` is the plural form of `withResource`. Only the source invokes the action; resource changes do not. Each source
emission samples the current resource tuple, so replacements are visible without hiding `getValue` calls inside the callback.

## Operators

| Operator                                    | Behavior                                                                                           |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `afterSettle()`                             | Re-emit synchronously after the current propagation wave settles                                   |
| `map(fn, distinct?)`                        | Transform each value; optional distinct filter on the output                                       |
| `filter(predicate)`                         | Drop values failing the predicate; supports type-guard predicates for narrowing                    |
| `filterMap(project, distinct?)`             | Project once, drop `null` and `undefined`, then compare retained values                            |
| `mapTo(value)`                              | Replace every emission with a constant                                                             |
| `scan((acc, value) => acc, seed)`           | Running accumulation                                                                               |
| `once()`                                    | Pass only the first emission                                                                       |
| `withLatestFrom(...nodes$)`                 | Append the latest values of other nodes to each source emission; emits only when the source emits  |
| `throttleTime(ms, distinct?)`               | Rate-limit emissions; optional distinct filter on the output                                       |
| `debounceTime(ms, distinct?)`               | Emit only after the source goes quiet for the duration; optional distinct filter on the output     |
| `delayWithMicrotask()`                      | Re-emit in a microtask, after the current cycle                                                    |
| `onNext(buf$)`                              | Buffer the source value, emit `[buffered, value]` when `buf$` next emits                           |
| `handlePromise(onLoad, onSuccess, onError)` | Expand a promise-emitting node into loading/success/error emissions                                |
| `switchMapPromise(project, options?)`       | Abort prior Promise work and emit only the latest input-correlated success or error                |
| `concatMapPromise(project, options?)`       | Run Promise work one at a time in arrival order and emit every result in order                     |
| `coalescePromise(project, options?)`        | Run one Promise at a time and keep only the newest waiting input; for writes                       |
| `exhaustMapPromise(project, options?)`      | Run one Promise at a time and ignore inputs that arrive while it runs; for duplicate-prone actions |

Two distinctions that prevent common mistakes:

- `combine` vs `withLatestFrom`: `combine` emits when _any_ input changes; `withLatestFrom` only when the _source_ emits, with the other nodes read passively. Use `withLatestFrom` for "when the user clicks, read the current settings", `combine` for "recompute whenever anything changes".
- `map(..., distinct)` vs node distinct: pass `false` as map's distinct when piping into a Trigger-like sink that must fire every time — for example mapping mutation successes to `undefined` for a refetch trigger:
- `filterMap(project, distinct)` vs `map` followed by `filter`: `filterMap` applies distinctness only after it drops nullish results.
  Pass `false` when repeated equal retained values are independent events. A dropped value does not reset the last retained value.
- `debounceTime(ms, distinct)` and `throttleTime(ms, distinct)`: both are distinct by default, so a `Trigger` piped through them
  fires once and every later burst is suppressed as an equal `undefined`. Pass `false` when each settled burst is an independent
  event, such as coalescing refetch requests. Keep the default when repeated equal values should collapse, such as a search
  term that settles back to its previous text.
- `afterSettle()` vs `delayWithMicrotask()`: `afterSettle` remains synchronous and completes before `pub` returns. It waits for graph
  propagation only. `delayWithMicrotask` leaves the current call stack and starts a later transaction.
- `handlePromise` vs `switchMapPromise`: `handlePromise` can emit loading state and allows every Promise to settle. `switchMapPromise`
  is latest-only, passes an `AbortSignal`, and always retains the source input in its success or error result.
- `switchMapPromise` vs `coalescePromise` and `concatMapPromise`: switching is for reads. Aborting a request does not undo it on the
  server, so a switched write can leave the server on an older value than the UI shows. Use `coalescePromise` or `concatMapPromise`
  for writes; see [Ordered Promise writes](#ordered-promise-writes).

```ts
e.link(
  e.pipe(
    e.merge(create.data$, remove.data$),
    e.filter((r) => r.type === 'success'),
    e.map(() => undefined, false) // without false, the second success would be filtered as a duplicate undefined
  ),
  tasksQuery.refetch$
)
```

## Latest-only Promise work

Use `switchMapPromise` when each new input supersedes pending asynchronous work:

```ts
const result$ = e.pipe(
  request$,
  e.switchMapPromise((request, signal) => fetchResult(request, signal))
)

e.sub(result$, (result) => {
  if (result.status === 'success') {
    console.log(result.input, result.value)
  } else {
    console.error(result.input, result.error)
  }
})
```

A new input aborts the previous signal before the new projector runs. Abort is advisory: old work may ignore it, but generation checks
still prevent stale fulfillment or rejection from publishing. Engine disposal aborts current work and suppresses later settlement.

Synchronous projector throws and current Promise rejections become `{ status: 'error', input, error }`. The operator does not classify
errors by name. Superseded and disposed generations stay silent regardless of their rejection shape; a current live rejection emits even
when its error resembles an abort error. The result stream is non-distinct, so equal values and reused error objects remain observable.

Removing an output subscription does not cancel already activated work. The Engine owns the operator lifecycle; dispose it to abort and
invalidate pending work.

## Ordered Promise writes

`switchMapPromise` guarantees that the UI sees the newest _response_. It does not guarantee that the server ends on the newest _value_:
aborting a client request does not cancel one the server already received, so quick successive writes can be applied in any order.

Three operators keep writes from overlapping. All emit the same `SwitchMapPromiseResult` as `switchMapPromise`, including `input`:

| Operator            | While work is in flight                                            | Three quick inputs `A`, `B`, `C`  |
| ------------------- | ------------------------------------------------------------------ | --------------------------------- |
| `concatMapPromise`  | Queues every input and runs them one at a time in arrival order    | `A`, then `B`, then `C`           |
| `coalescePromise`   | Keeps only the newest waiting input and sends it when work settles | `A`, then `C`; `B` never starts   |
| `exhaustMapPromise` | Ignores every input that arrives while work runs                   | `A` only; `B` and `C` never start |

Use `exhaustMapPromise` when a second input is a duplicate, such as a double click on a submit button, and the other two when
every input carries a value that must reach the server. With `exhaustMapPromise`, a key frees as soon as its work settles, so a
subscriber of the result can already start new work for it. `concatMapPromise` and `coalescePromise` hold the key while result
subscribers run, and start the next waiting input after them.

The next input starts when the current work settles, whether it succeeded or failed. None of the three aborts running work; only engine
disposal does, and it also drops waiting inputs. A `coalescePromise` input that is replaced while waiting never starts and emits nothing.

```ts
const saved$ = e.pipe(
  setValue$,
  e.coalescePromise((value, signal) => api.save(value, { signal }))
)
```

### Per-key ordering

Writes are usually scoped to a record. Pass `key` so ordering, coalescing, or switching applies per key, and different keys run
independently. A write for record `b` then never waits for, replaces, or aborts a write for record `a`. `switchMapPromise` accepts
`key` as well.

```ts
const saved$ = e.pipe(
  setSetting$,
  e.coalescePromise(({ id, value }, signal) => api.patch(id, value, { signal }), { key: ({ id }) => id })
)
```

Keys are compared like `Map` keys, so use strings or numbers rather than freshly created objects.

### Merging partial updates

By default `coalescePromise` replaces the waiting input with the newest one, which is right when each input is the full value for its
key. When inputs are partial patches, replacing loses changes: after `{ a: 1 }` and `{ b: 2 }` wait behind running work, only
`{ b: 2 }` would be sent. Pass `merge` to combine them. It receives the waiting input and the newer one for the same key, and is
never called with the input that is already running. The merged value becomes the next input and its result's `input`.

```ts
e.coalescePromise(({ id, patch }, signal) => api.patch(id, patch, { signal }), {
  key: ({ id }) => id,
  merge: (waiting, next) => ({ id: next.id, patch: { ...waiting.patch, ...next.patch } }),
})
```

## The low-level primitive: connect

Every operator and combinator reduces to `engine.connect({ sources, pulls, sink, map })`: when any node in `sources` emits, call `map(done)(...sourceValues, ...pullValues)`; calling `done(value)` proposes an emission on `sink` (still subject to the sink's distinct check). `pulls` are read passively without triggering. Reach for `connect` only when no operator combination expresses the dependency shape — it is the engine's assembly language.
