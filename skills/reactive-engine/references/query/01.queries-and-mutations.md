title: Queries and Mutations
description: Data fetching as nodes - lifecycle, result states, retries, and wiring patterns.
---

`@virtuoso.dev/reactive-engine-query` expresses data fetching as engine nodes, so queries compose with the rest of the graph: route params can drive query params, mutation successes can trigger refetches, and components consume results with `useCellValue` like any other state.

## Query

```ts
export const tasksQuery = Query<{ listId: string }, Task[]>({
  queryFn: async ({ listId }, signal) => {
    const res = await fetch(`/api/tasks?listId=${listId}`, { signal })
    if (!res.ok) throw new Error('Failed to fetch tasks')
    return res.json()
  },
  initialParams: { listId: '' },
})
```

`Query()` returns a bundle of nodes:

| Node          | Kind    | Role                                                        |
| ------------- | ------- | ----------------------------------------------------------- |
| `data$`       | Cell    | The query result (discriminated union below)                |
| `params$`     | Cell    | Publishing new params re-executes the query                 |
| `refetch$`    | Trigger | Re-execute with current params                              |
| `invalidate$` | Trigger | Mark stale: keep showing data, set `isFetching`, re-execute |
| `unload$`     | Trigger | Abort, clear data, return to pending                        |
| `enabled$`    | Cell    | Gate execution; toggling to `true` executes                 |

Options: `enabled` (default `true`), `retry` (default `3`; `retry: 3` means up to 4 attempts), `retryDelay` (default exponential backoff capped at 30s), `refetchInterval` (polling, starts after a successful fetch), `initialData`.

### Result shape

`data$` emits one of three states, discriminated on `type`:

```ts
{ type: 'pending', data: null,  isLoading: true,  isFetching: true,  isSuccess: false, isError: false, error: null }
{ type: 'success', data: T,     isLoading: false, isFetching: boolean, isSuccess: true,  isError: false, error: null, dataUpdatedAt: number }
{ type: 'error',   data: null,  isLoading: false, isFetching: false, isSuccess: false, isError: true,  error: unknown }
```

`isFetching: true` inside the success state means a background refresh is in flight while stale data stays visible — that is what `invalidate$` produces, versus `unload$` which drops to pending.

### Lifecycle rules

- A query executes when its `data$` first activates in an engine (if enabled), whenever `params$` emits (if enabled), on `refetch$`/`invalidate$`, and when `enabled$` flips to `true`.
- Each execution aborts the previous in-flight request — the `signal` passed to `queryFn` must reach the actual fetch.
- Disabling aborts in-flight work and stops polling.
- Query state is per engine, like all node state; the same query in two engines fetches independently.

## Mutation

```ts
export const createTask = Mutation<{ listId: string; title: string }, Task>({
  mutationFn: async (params, signal) => {
    /* POST */
  },
})
```

`Mutation()` returns a bundle of nodes. Each concern has its own node: what to show, what happened to each call, and how much work
is left.

| Node            | Kind   | Role                                                                                      |
| --------------- | ------ | ----------------------------------------------------------------------------------------- |
| `mutate$`       | Stream | Publish params to make a call                                                             |
| `settled$`      | Stream | One outcome per call: `success`, `error`, or `dropped`; never suppressed                  |
| `data$`         | Cell   | What to display: the latest start or result among calls made since the last `reset$`      |
| `pendingCount$` | Cell   | Number of calls that are running or waiting to start                                      |
| `reset$`        | Stream | Return `data$` to idle; running and waiting calls continue and still report on `settled$` |
| `dropWaiting$`  | Stream | Drop every call that is waiting to start; each one ends as `dropped`                      |

Mutations never auto-execute and don't retry by default. Publishing equal params twice makes two calls.

**A call that started is never aborted.** Aborting a request does not undo it on the server, so a mutation that hid an aborted call
could leave the UI showing a value the server no longer has. The `AbortSignal` passed to `mutationFn(params, signal)` is aborted only
when the engine is disposed; pass it to `fetch` so disposal cancels the request.

`onSuccess(data, params, engine)` and `onError(error, params, engine)` run for every call that succeeds or fails, including calls
made before a `reset$`. They run after the publish that delivered the outcome has settled, so `data$` and `settled$` subscribers always
see an outcome before a callback starts another mutation; use `engine.pub` in them to write back into the graph.

### Outcomes: `settled$`

Every call ends with exactly one event on `settled$`:

```ts
{ type: 'success', params: TParams, data: T }
{ type: 'error',   params: TParams, error: unknown }
{ type: 'dropped', params: TParams }
```

- `success` and `error`: the call ran. After an `error`, the server may or may not have applied the request, so reconcile, for
  example by refetching.
- `dropped`: the call never started, so the server never received it. A newer call replaced it while it waited under
  `concurrency: 'coalesce'` without `merge`, or `dropWaiting$` removed it.

Params merged into a waiting call share that call's outcome. Wire anything that must react to what happened on the server, such as
refetches, confirmed state, and optimistic overlays, to `settled$` or to the callbacks. Neither is affected by `reset$`.

### Display state: `data$`

```ts
{ type: 'idle',    data: null, isPending: false, isSuccess: false, isError: false, error: null }
{ type: 'pending', data: null, isPending: true,  isSuccess: false, isError: false, error: null,    params: TParams }
{ type: 'success', data: T,    isPending: false, isSuccess: true,  isError: false, error: null,    params: TParams }
{ type: 'error',   data: null, isPending: false, isSuccess: false, isError: true,  error: unknown, params: TParams }
```

`data$` shows the latest start or result among calls made since the last `reset$`, so it is safe to clear, for example to dismiss an
error message. A call made before the reset never shows up in `data$` again, but it still runs and reports on `settled$`. Calls that
wait or are dropped do not change `data$`.

When calls overlap, `isPending` describes the latest event only: one call can succeed while another still runs. Read `pendingCount$`
to know whether anything is still running or waiting; `pendingCount$ > 0` is the accurate busy flag.

### Concurrency

`concurrency` decides how overlapping calls are scheduled. With `'serial'` or `'coalesce'`, pass `key` to apply the policy per
record, so calls for different keys run independently.

| `concurrency`          | Overlapping calls                                                               |
| ---------------------- | ------------------------------------------------------------------------------- |
| `'parallel'` (default) | Every call starts immediately; results arrive in completion order               |
| `'serial'`             | Calls run one at a time in arrival order                                        |
| `'coalesce'`           | One call runs at a time; while it runs, only the newest waiting params are kept |

TypeScript rejects options that a policy would ignore: `key` with `'parallel'`, and `merge` with anything but `'coalesce'`.

Use `'coalesce'` with a key for controls that save on every interaction, such as toggles or steppers: the server ends on the last value,
with at most one request per record in flight. If params are partial updates, pass `merge` so waiting updates are combined instead of
replaced; otherwise earlier changes are never sent:

```ts
export const saveSetting = Mutation<{ id: string; patch: Patch }, Saved>({
  mutationFn: ({ id, patch }, signal) => api.patch(id, patch, { signal }),
  concurrency: 'coalesce',
  key: ({ id }) => id,
  merge: (waiting, next) => ({ id: next.id, patch: { ...waiting.patch, ...next.patch } }),
})
```

Params are inferred from `mutationFn`. Pass the type arguments explicitly, as above, or list `mutationFn` before `key` and `merge`;
otherwise TypeScript may infer params as `unknown`.

### Optimistic updates

Overlay pending edits on confirmed state with a `ComputedCell`. Give each edit a revision, and let each call carry the revisions it
covers; `merge` concatenates them. Every outcome on `settled$` then removes exactly the edits of its own call. A failed or dropped edit
disappears as soon as its call ends, newer edits for the same record stay visible until their calls end, and `reset$` cannot strand or
lose an edit:

```ts
interface Save {
  id: string
  patch: Patch
  revs: number[]
}

const saveSetting = Mutation<Save, Saved>({
  mutationFn: ({ id, patch }, signal) => api.patch(id, patch, { signal }),
  concurrency: 'coalesce',
  key: ({ id }) => id,
  merge: (waiting, next) => ({ id: next.id, patch: { ...waiting.patch, ...next.patch }, revs: [...waiting.revs, ...next.revs] }),
})

interface Edit {
  id: string
  patch: Patch
  rev: number
}

const confirmed$ = Cell<Map<string, Saved>>(new Map())
const edits$ = Cell<Edit[]>([])
const visible$ = ComputedCell([confirmed$, edits$], ([confirmed, edits]) => overlay(confirmed, edits))

let lastRev = 0
const edit$ = e.pipe(
  setSetting$,
  e.map(({ id, patch }): Edit => ({ id, patch, rev: ++lastRev }), false)
)
e.changeWith(edits$, edit$, (edits, edit) => [...edits, edit])
e.link(
  e.pipe(
    edit$,
    e.map(({ id, patch, rev }): Save => ({ id, patch, revs: [rev] }), false)
  ),
  saveSetting.mutate$
)

e.changeWith(confirmed$, saveSetting.settled$, (confirmed, outcome) =>
  outcome.type === 'success' ? new Map(confirmed).set(outcome.params.id, outcome.data) : confirmed
)
e.changeWith(edits$, saveSetting.settled$, (edits, outcome) => edits.filter((edit) => !outcome.params.revs.includes(edit.rev)))
// After an error, refetch the record: the server may have applied the request.
```

```tsx
const create = usePublisher(createTask.mutate$)
const result = useCellValue(createTask.data$)

<button disabled={result.isPending} onClick={() => create({ listId, title })}>Add</button>
```

## Wiring patterns

**Mutations trigger refetches in the graph, not in components.** Declare the relationship once at module scope:

```ts
e.link(
  e.pipe(
    e.merge(createTask.settled$, updateTask.settled$, deleteTask.settled$),
    e.filter((outcome) => outcome.type !== 'dropped'), // every call that reached the server, even if it failed
    e.map(() => undefined, false) // distinct=false: consecutive outcomes must each fire
  ),
  tasksQuery.refetch$
)
```

**Routes drive query params.** A route node emits its params when matched; pipe it into `params$`:

```ts
e.link(
  e.pipe(
    tasks$, // Route('/lists/{id:string}', TasksPage)
    e.filter((params) => params !== null),
    e.map((params) => ({ listId: params.id }))
  ),
  tasksQuery.params$
)
```

Navigation then transparently refetches — no effect hooks, no param threading through components.

**Dependent queries** gate on their prerequisite:

```ts
e.link(
  e.pipe(
    userQuery.data$,
    e.map((r) => r.type === 'success')
  ),
  ordersQuery.enabled$
)
```

## Rendering results

Branch on the discriminated union:

```tsx
const result = useCellValue(tasksQuery.data$)

if (result.isLoading) return <Spinner />
if (result.isError) return <ErrorView error={result.error} />
return <TaskList tasks={result.data} refreshing={result.isFetching} />
```
