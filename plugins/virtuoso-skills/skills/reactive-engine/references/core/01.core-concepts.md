The reactive engine models application logic as a graph of typed nodes. Two ideas carry everything else:

1. **Nodes are definitions, not state.** A node constructor returns an inert reference — at runtime it is literally a `Symbol`. Creating a node records its definition (type, initial value, distinct behavior) in a global registry, but holds no value.
2. **Engines hold state.** An `Engine` instance activates nodes on first use and owns their values. The same node used by two engines has two independent values.

```ts
import { Cell, Engine } from '@virtuoso.dev/reactive-engine-core'

const count$ = Cell(0) // a definition, usually at module scope

const a = new Engine()
const b = new Engine()
a.pub(count$, 5)
a.getValue(count$) // 5
b.getValue(count$) // 0 — independent state
```

This split is what makes the engine suitable for building reusable components: a library defines its node graph once at module scope, and every component instance gets its own engine — its own state — without re-declaring anything.

## Node types

| Node                                     | State          | Emits                  | Use for                                            |
| ---------------------------------------- | -------------- | ---------------------- | -------------------------------------------------- |
| `Cell(initial, distinct?)`               | Current value  | On value change        | App state and configuration                        |
| `ComputedCell(dependencies, project, …)` | Current value  | On projected change    | State derived from current readable state          |
| `DerivedCell(initial, source$)`          | Current value  | When the source emits  | State driven by an arbitrary stream                |
| `Stream<T>(distinct?)`                   | None           | On publish             | Events, commands, transient data                   |
| `Trigger()`                              | None           | On publish (valueless) | "Something happened" signals                       |
| `Pulsar(cadence$, options?)`             | None           | On scheduled pulse     | Polling and heartbeat signals                      |
| `Resource(factory)`                      | Factory result | —                      | Per-engine objects with setup/teardown             |
| `Pipe<T>(...operators)`                  | —              | —                      | An input/output node pair with a transform between |

```ts
import { Cell, Pulsar, Resource, Stream, Trigger } from '@virtuoso.dev/reactive-engine-core'

const theme$ = Cell<'light' | 'dark'>('light')
const keyPressed$ = Stream<string>()
const reset$ = Trigger()
const pollIntervalMs$ = Cell<number | null>(null)
const poll$ = Pulsar(pollIntervalMs$, { leading: true })
const cache$ = Resource(() => ({
  data: new Map<string, unknown>(),
  dispose() {
    this.data.clear()
  },
}))
```

`Pulsar` reads its cadence when the output first activates in an engine. A positive finite number arms it; `null` disarms it. Pulses
carry no payload. Sample a clock or map the pulse when a timestamp is needed. See [Engine and Lifecycle](./02.engine-and-lifecycle.md#activation-scoped-timers)
for leading, retuning, and cleanup behavior.

A `Resource` factory runs once per engine, the first time the engine touches the node. On `engine.dispose()` the engine calls the instance's `[Symbol.dispose]()` if present, falling back to `dispose()`.

`DerivedCell` is a cell whose value tracks a source expression:

```ts
import { DerivedCell, e } from '@virtuoso.dev/reactive-engine-core'

const fahrenheit$ = DerivedCell(
  32,
  e.pipe(
    celsius$,
    e.map((c) => c * 1.8 + 32)
  )
)
```

Components read it like any cell; nothing can publish into it directly without going through the source.

Use `ComputedCell` when the result is a pure function of readable state:

```ts
import { Cell, ComputedCell } from '@virtuoso.dev/reactive-engine-core'

const price$ = Cell(0)
const quantity$ = Cell(1)
const total$ = ComputedCell([price$, quantity$], ([price, quantity]) => price * quantity)
```

`Cell`, `DerivedCell`, and `ComputedCell` return `StateRef<T>`. TypeScript accepts only these readable state references as
`ComputedCell` dependencies. JavaScript and cast inputs receive the same check at runtime. Streams, triggers, and resources are not
valid dependencies.

On first activation, the computed cell reads its dependencies, runs its projection once, and stores the result. This does not publish
the dependencies or notify computed-cell subscribers. Later changes to any dependency recompute the value. A `pubIn` batch runs the
projection once with all settled values, and the optional comparator controls whether the result emits.

This initialization rule is the important difference from `DerivedCell`. A derived cell keeps its declared initial value until its
arbitrary source emits. A computed cell can initialize from current state because its readable dependencies and projection are explicit.

## Distinct semantics

Every Cell and Stream filters duplicate emissions by default:

- `true` (default) — compare with `===` (the `defaultComparator`; reference equality, not deep equality)
- `false` — never filter; every publish emits
- `(prev, next) => boolean` — custom comparator returning `true` when values are equal (suppress emission)

```ts
const user$ = Cell<User | null>(null, (prev, next) => prev?.id === next?.id)
```

Use the comparator helpers when identity is composed from repeated shapes:

```ts
const control$ = Cell(
  initialControl,
  equalBy(
    (value) => value.disabled,
    (value) => value.durationMs
  )
)

const selected$ = Cell<Item | null>(
  null,
  equalNullable((left, right) => left.id === right.id)
)
const visibleIds$ = Cell<readonly string[]>([], (previous, current) => equalArrays(previous, current))
```

`equalBy` makes the fields that define observable identity explicit. `equalNullable` applies a domain comparator only to two non-null
values. `equalArrays` compares length and position, uses `Object.is` for items by default, and accepts a domain item comparator. These
helpers compose an identity decision; they cannot determine which fields are meaningful for an application.

Two consequences worth internalizing:

- Because the default is reference equality, publishing a mutated object does not emit. Always publish new references (`new Map(old)`, spread), the same discipline React state requires.
- A stream's first candidate always emits without invoking its comparator. Later candidates compare with the last emitted value.
- A state node compares with its current value. `prev` can be `undefined` when the state itself stores `undefined`, so custom comparators must handle that value.

Triggers never filter; every publish fires.

## The `e` namespace

The package exports each operator and combinator individually, and also bundles them in a single `e` object — convenient when wiring many connections:

```ts
import { e } from '@virtuoso.dev/reactive-engine-core'

e.link(
  e.pipe(
    toggleTheme$,
    e.withLatestFrom(theme$),
    e.map(([, current]) => (current === 'light' ? 'dark' : 'light'))
  ),
  theme$
)
```

`e` contains the combinators (`link`, `pipe`, `combine`, `merge`, `sub`, `changeWith`, ...), the operators (`map`, `filter`, `scan`, ...), and the context-bound utilities (`pub`, `getValue`, `pubIn` — see [Engine and Lifecycle](./02.engine-and-lifecycle.md) for where those are allowed).

## Naming conventions

- Node references take a `$` suffix: `count$`, `setColumnVisibility$`.
- Input streams that represent user actions read as commands: `resizeColumn$`, `toggleTheme$`.
- State cells read as nouns: `theme$`, `scrollLocation$`.
- Plain helper functions take no suffix.

These conventions come from the packages built on the engine (data-table follows them throughout) and make the input/output boundary of a module visible at a glance.
