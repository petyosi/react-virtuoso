title: Queries and Mutations
description: Data fetching as nodes - lifecycle, result states, retries, and wiring patterns.
---

`@virtuoso.dev/reactive-engine-query` expresses data fetching as engine nodes, so queries compose with the rest of the graph: route params can drive query params, mutation successes can trigger refetches, and components consume results with `useCellValue` like any other state.

## Query

```ts
export const tasksQuery = Query<{ listId: string }, Task[]>({
  queryFn: async ({ listId }, signal) => {
    const res = await fetch(`/api/tasks?listId=${listId}`, { signal })
    if (!res.ok) throw new Error('Failed to fetch tasks')
    return res.json()
  },
  initialParams: { listId: '' },
})
```

`Query()` returns a bundle of nodes:

| Node          | Kind    | Role                                                        |
| ------------- | ------- | ----------------------------------------------------------- |
| `data$`       | Cell    | The query result (discriminated union below)                |
| `params$`     | Cell    | Publishing new params re-executes the query                 |
| `refetch$`    | Trigger | Re-execute with current params                              |
| `invalidate$` | Trigger | Mark stale: keep showing data, set `isFetching`, re-execute |
| `unload$`     | Trigger | Abort, clear data, return to pending                        |
| `enabled$`    | Cell    | Gate execution; toggling to `true` executes                 |

Options: `enabled` (default `true`), `retry` (default `3`; `retry: 3` means up to 4 attempts), `retryDelay` (default exponential backoff capped at 30s), `refetchInterval` (polling, starts after a successful fetch), `initialData`.

### Result shape

`data$` emits one of three states, discriminated on `type`:

```ts
{ type: 'pending', data: null,  isLoading: true,  isFetching: true,  isSuccess: false, isError: false, error: null }
{ type: 'success', data: T,     isLoading: false, isFetching: boolean, isSuccess: true,  isError: false, error: null, dataUpdatedAt: number }
{ type: 'error',   data: null,  isLoading: false, isFetching: false, isSuccess: false, isError: true,  error: unknown }
```

`isFetching: true` inside the success state means a background refresh is in flight while stale data stays visible — that is what `invalidate$` produces, versus `unload$` which drops to pending.

### Lifecycle rules

- A query executes when its `data$` first activates in an engine (if enabled), whenever `params$` emits (if enabled), on `refetch$`/`invalidate$`, and when `enabled$` flips to `true`.
- Each execution aborts the previous in-flight request — the `signal` passed to `queryFn` must reach the actual fetch.
- Disabling aborts in-flight work and stops polling.
- Query state is per engine, like all node state; the same query in two engines fetches independently.

## Mutation

```ts
export const createTask = Mutation<{ listId: string; title: string }, Task>({
  mutationFn: async (params) => {
    /* POST */
  },
})
```

`Mutation()` returns a bundle of nodes:

| Node            | Kind   | Role                                                               |
| --------------- | ------ | ------------------------------------------------------------------ |
| `data$`         | Cell   | The latest mutation event (`idle \| pending \| success \| error`)  |
| `mutate$`       | Stream | Publish params to execute                                          |
| `pendingCount$` | Cell   | Number of calls that are running or waiting; derived from `data$`  |
| `reset$`        | Stream | Abort running calls, drop waiting ones, and return `data$` to idle |

Mutations never auto-execute and don't retry by default. `mutationFn(params, signal)` receives an `AbortSignal` that is aborted by
`reset$`, by a newer call under `concurrency: 'switch'`, and on engine disposal; pass it to `fetch`. A retry delay stops when the signal
aborts. Publishing equal params twice runs two calls, and every `reset$` acts. `onSuccess(data, params, engine)` and
`onError(error, params, engine)` run after the publish that delivered the result has settled, so `data$` subscribers always see a result
before a callback starts or resets another mutation; use `engine.pub` in them to write back into the graph.

### Result shape

Pending, success, and error results include the `params` of the call they describe, so graph wiring can match each response to its
request. Every result also carries `pendingCount`, the number of calls running or waiting after that event:

```ts
{ type: 'idle',    data: null, isPending: false, isSuccess: false, isError: false, error: null,                      pendingCount: 0 }
{ type: 'pending', data: null, isPending: true,  isSuccess: false, isError: false, error: null,    params: TParams, pendingCount: number }
{ type: 'success', data: T,    isPending: false, isSuccess: true,  isError: false, error: null,    params: TParams, pendingCount: number }
{ type: 'error',   data: null, isPending: false, isSuccess: false, isError: true,  error: unknown, params: TParams, pendingCount: number }
```

`data$` holds the latest event, so its `isPending` describes that event only. When calls overlap, one can succeed while another still
runs; `pendingCount` says whether anything is still running or waiting. A call that waits without starting re-emits the latest result
with the new count, so handlers on `data$` should be idempotent.

Read the count from the result inside `data$` subscribers. `pendingCount$` is derived from `data$`, so its subscribers can read
`data$` and get the matching result, but a `data$` subscriber that reads `pendingCount$` sees the previous count: subscribers run as
each node updates, before the nodes that depend on it.

### Concurrency

`concurrency` decides how overlapping calls are scheduled. Pass `key` to apply it per record, so calls for different keys run
independently. `parallel` ignores `key`.

| `concurrency`          | Overlapping calls                                                                |
| ---------------------- | -------------------------------------------------------------------------------- |
| `'parallel'` (default) | Every call starts immediately; results arrive in completion order                |
| `'serial'`             | Calls run one at a time in arrival order                                         |
| `'coalesce'`           | One call runs at a time; while it runs, only the newest waiting params are kept  |
| `'switch'`             | A new call aborts the running one, which then never reaches `data$` or callbacks |

Use `'coalesce'` with a key for controls that save on every interaction, such as toggles or steppers: the server ends on the last value,
with at most one request per record in flight. Aborting a request does not undo it on the server, so prefer `'coalesce'` or `'serial'`
over `'switch'` for writes. If params are partial updates, pass `merge` so waiting updates are combined instead of replaced; otherwise
earlier changes are never sent:

```ts
export const saveSetting = Mutation<{ id: string; patch: Patch }, Saved>({
  mutationFn: ({ id, patch }, signal) => api.patch(id, patch, { signal }),
  concurrency: 'coalesce',
  key: ({ id }) => id,
  merge: (waiting, next) => ({ id: next.id, patch: { ...waiting.patch, ...next.patch } }),
})
```

Params are inferred from `mutationFn`. Pass the type arguments explicitly, as above, or list `mutationFn` before `key` and `merge`;
otherwise TypeScript may infer params as `unknown`.

### Optimistic updates

Overlay pending edits on confirmed state with a `ComputedCell`. Give each edit a revision, and remove the edits a call covers when
that call settles: with `merge`, the merged call carries the newest revision of the edits it combines. A failed edit then disappears as
soon as its own call fails, newer edits for the same record stay visible until their calls settle, and `reset$` clears every overlay:

```ts
interface Edit {
  id: string
  patch: Patch
  rev: number
}

const saveSetting = Mutation<Edit, Saved>({
  mutationFn: ({ id, patch }, signal) => api.patch(id, patch, { signal }),
  concurrency: 'coalesce',
  key: ({ id }) => id,
  merge: (waiting, next) => ({ ...next, patch: { ...waiting.patch, ...next.patch } }),
})

const confirmed$ = Cell<Map<string, Saved>>(new Map())
const pending$ = Cell<Edit[]>([])
const visible$ = ComputedCell([confirmed$, pending$], ([confirmed, pending]) => overlay(confirmed, pending))

let lastRev = 0
const edit$ = e.pipe(
  setSetting$,
  e.map(({ id, patch }): Edit => ({ id, patch, rev: ++lastRev }), false)
)
e.changeWith(pending$, edit$, (pending, edit) => [...pending, edit])
e.link(edit$, saveSetting.mutate$)

e.changeWith(confirmed$, saveSetting.data$, (confirmed, result) =>
  result.type === 'success' ? new Map(confirmed).set(result.params.id, result.data) : confirmed
)
e.changeWith(pending$, saveSetting.data$, (pending, result) => {
  if (result.type === 'idle') return [] // reset$ dropped every call
  if (result.type !== 'success' && result.type !== 'error') return pending
  const { id, rev } = result.params
  return pending.filter((edit) => edit.id !== id || edit.rev > rev)
})
```

```tsx
const create = usePublisher(createTask.mutate$)
const result = useCellValue(createTask.data$)

<button disabled={result.isPending} onClick={() => create({ listId, title })}>Add</button>
```

## Wiring patterns

**Mutations trigger refetches in the graph, not in components.** Declare the relationship once at module scope:

```ts
e.link(
  e.pipe(
    e.merge(createTask.data$, updateTask.data$, deleteTask.data$),
    e.filter((r) => r.type === 'success'),
    e.map(() => undefined, false) // distinct=false: consecutive successes must each fire
  ),
  tasksQuery.refetch$
)
```

**Routes drive query params.** A route node emits its params when matched; pipe it into `params$`:

```ts
e.link(
  e.pipe(
    tasks$, // Route('/lists/{id:string}', TasksPage)
    e.filter((params) => params !== null),
    e.map((params) => ({ listId: params.id }))
  ),
  tasksQuery.params$
)
```

Navigation then transparently refetches — no effect hooks, no param threading through components.

**Dependent queries** gate on their prerequisite:

```ts
e.link(
  e.pipe(
    userQuery.data$,
    e.map((r) => r.type === 'success')
  ),
  ordersQuery.enabled$
)
```

## Rendering results

Branch on the discriminated union:

```tsx
const result = useCellValue(tasksQuery.data$)

if (result.isLoading) return <Spinner />
if (result.isError) return <ErrorView error={result.error} />
return <TaskList tasks={result.data} refreshing={result.isFetching} />
```
