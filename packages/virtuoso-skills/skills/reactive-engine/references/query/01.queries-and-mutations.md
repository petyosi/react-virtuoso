title: Queries and Mutations
description: Data fetching as nodes - lifecycle, result states, retries, and wiring patterns.
---

`@virtuoso.dev/reactive-engine-query` expresses data fetching as engine nodes, so queries compose with the rest of the graph: route params can drive query params, mutation successes can trigger refetches, and components consume results with `useCellValue` like any other state.

## Query

```ts
export const tasksQuery = Query<{ listId: string }, Task[]>({
  queryFn: async ({ listId }, signal) => {
    const res = await fetch(`/api/tasks?listId=${listId}`, { signal })
    if (!res.ok) throw new Error('Failed to fetch tasks')
    return res.json()
  },
  initialParams: { listId: '' },
})
```

`Query()` returns a bundle of nodes:

| Node          | Kind    | Role                                                        |
| ------------- | ------- | ----------------------------------------------------------- |
| `data$`       | Cell    | The query result (discriminated union below)                |
| `params$`     | Cell    | Publishing new params re-executes the query                 |
| `refetch$`    | Trigger | Re-execute with current params                              |
| `invalidate$` | Trigger | Mark stale: keep showing data, set `isFetching`, re-execute |
| `unload$`     | Trigger | Abort, clear data, return to pending                        |
| `enabled$`    | Cell    | Gate execution; toggling to `true` executes                 |

Options: `enabled` (default `true`), `retry` (default `3`; `retry: 3` means up to 4 attempts), `retryDelay` (default exponential backoff capped at 30s), `refetchInterval` (polling, starts after a successful fetch), `initialData`.

### Result shape

`data$` emits one of three states, discriminated on `type`:

```ts
type QueryShape<T> =
  | { type: 'pending'; data: null; isLoading: true; isFetching: true; isSuccess: false; isError: false; error: null; dataUpdatedAt: null }
  | { type: 'success'; data: T; isLoading: false; isFetching: boolean; isSuccess: true; isError: false; error: null; dataUpdatedAt: number }
  | { type: 'error'; data: null; isLoading: false; isFetching: false; isSuccess: false; isError: true; error: unknown; dataUpdatedAt: null }
```

`isFetching: true` inside the success state means a background refresh is in flight while stale data stays visible — that is what `invalidate$` produces, versus `unload$` which drops to pending.

### Lifecycle rules

- A query executes when its `data$` first activates in an engine (if enabled), whenever `params$` emits (if enabled), on `refetch$`/`invalidate$`, and when `enabled$` flips to `true`.
- Each execution aborts the previous in-flight request — the `signal` passed to `queryFn` must reach the actual fetch.
- Disabling aborts in-flight work and stops polling.
- Query state is per engine, like all node state; the same query in two engines fetches independently.

## Writes: Mutation or ConcurrentMutation

Two primitives write to a server. Pick one by asking: **if a second call for the same record arrives while the first is
running, does it carry new information that must reach the server?**

- **No.** It is a duplicate, for example a double click on "Delete" or "Charge card". Use `Mutation`: it runs one call
  per record and ignores the duplicate. Disable the control while the record is pending.
- **Yes.** It is a new value, for example a toggle's new state or the latest text in a field that autosaves. Use
  `ConcurrentMutation`, and pick its policy:
  - only the latest value matters: `concurrency: 'coalesce'`;
  - every call matters, in order: `concurrency: 'serial'`;
  - calls are independent of each other: `concurrency: 'parallel'`.

Both primitives share these rules:

- **`key` is required.** A key function makes one record per key, and the state is `status$`, a map. `key: false` makes
  the whole primitive one record, and the state is `data$`. Keys are strings or finite numbers; `1` and `'1'` are
  different keys.
- **A call that started is never aborted.** Aborting a request does not undo it on the server. The `AbortSignal` passed
  to `mutationFn(params, signal)` aborts only when the engine is disposed; pass it to `fetch`.
- **`settled$` reports outcomes, the state nodes show status.** Both carry `params`, and keyed ones carry `key`, so wiring
  can always match a response to its request.
- **Reconciliation that must run goes in `onSuccess` and `onError`.** For example, refetch the query there. A link from
  `settled$` works too, but a subscriber elsewhere that throws can make a link miss an emission, while callbacks always
  run.

## Mutation

```ts
export const deleteTask = Mutation<{ id: number }, void, number>({
  mutationFn: async ({ id }, signal) => {
    const res = await fetch(`/api/tasks/${id}`, { method: 'DELETE', signal })
    if (!res.ok) {
      throw new Error('Failed to delete task')
    }
  },
  key: ({ id }) => id,
  onSuccess: (_data, { id }, engine) => {
    engine.pub(tasksQuery.refetch$)
    engine.pub(deleteTask.dismiss$, id)
  },
})

export const createTask = Mutation<{ listId: string; title: string }, Task>({
  mutationFn: (params, signal) => api.createTask(params, signal),
  key: false,
  onSuccess: (_task, _params, engine) => {
    engine.pub(tasksQuery.refetch$)
  },
})
```

| Node          | `key: false`                                            | Keyed                                                           |
| ------------- | ------------------------------------------------------- | --------------------------------------------------------------- |
| `mutate$`     | Starts a call, unless one is in flight                  | Starts a call, unless the record has one in flight              |
| `data$`       | The record's `MutationResult`                           | —                                                               |
| `status$`     | —                                                       | `ReadonlyMap<key, MutationResult>`; a key with no entry is idle |
| `settled$`    | One outcome per input: `success`, `error`, or `ignored` | Same, each with `key`                                           |
| `dismiss$`    | Dismisses a settled result                              | Dismisses one record's settled result                           |
| `dismissAll$` | —                                                       | Dismisses every settled result                                  |

**One call per record.** A `mutate$` for a record that has a call in flight is **ignored**: `mutationFn` is not called,
`settled$` emits `{ type: 'ignored', params }`, and `onIgnored(params, engine)` runs. In development, an ignored call
also logs a warning, unless `onIgnored` is set. Pass `onIgnored` when ignoring is intended, for example as double-submit
protection. It should record or notify; never publish the same params to `mutate$` again from it, which loops until the
drain limit throws.

```tsx
function DeleteButton({ id }: { id: number }) {
  const status = useCellValue(deleteTask.status$)
  const remove = usePublisher(deleteTask.mutate$)
  return (
    <button disabled={status.get(id)?.isPending === true} onClick={() => remove({ id })}>
      Delete
    </button>
  )
}
```

### Result shape

The 2.0.2 fields stay. Every state except `idle` carries the `params` of its call, and settled results carry `settledAt`:

```ts
type Shape =
  | { type: 'idle'; data: null; error: null; isPending: false; isSuccess: false; isError: false }
  | { type: 'pending'; data: null; error: null; isPending: true; isSuccess: false; isError: false; params: TParams }
  | { type: 'success'; data: TData; error: null; isPending: false; isSuccess: true; isError: false; params: TParams; settledAt: number }
  | { type: 'error'; data: null; error: unknown; isPending: false; isSuccess: false; isError: true; params: TParams; settledAt: number }
```

### When to dismiss

A result stays until the record's next call starts, or until it is dismissed. Dismiss never touches a pending call: on
a pending record it does nothing, and the result still appears when the call settles.

- **After a successful delete**, dismiss its key: the row is gone.
- **After a success message has been shown**, dismiss it.
- **For a record no longer on screen**, wait for its outcome. On success, dismiss it. On error, surface it first, for
  example in a toast or a list of failed saves, or retry it; dismiss only after that.
- **Never dismiss to switch** which record a pane shows. Read the selected key from `status$` instead.
- **Dismiss is not cancel.** A request that was sent cannot be called back. To undo it, send a compensating write.

### Typing

Pass the key type as the third type argument, as in `Mutation<{ id: number }, void, number>`. With only two type
arguments, a key function is a compile error, "No overload matches this call": add the key type. This keeps
`status.get(id)` and `dismiss$` typed with the real key, so a string route param cannot look up a numeric key by mistake.

Inference without type arguments also works when the `mutationFn` parameter is annotated, but it depends on the order
of the options when `mutationFn` has unannotated parameters, so the explicit form is preferred. An options object
declared on its own needs `key: false as const`.

## ConcurrentMutation

```ts
export const saveDone = ConcurrentMutation<Task, Task, number>({
  mutationFn: (task, signal) => api.updateTask(task, signal),
  concurrency: 'coalesce',
  key: (task) => task.id,
  onSuccess: (_task, _params, engine) => {
    engine.pub(tasksQuery.refetch$)
  },
})
```

| Node              | `key: false`                                           | Keyed                                                                    |
| ----------------- | ------------------------------------------------------ | ------------------------------------------------------------------------ |
| `mutate$`         | Makes a call, scheduled by the policy                  | Same, per record                                                         |
| `data$`           | The record's `ConcurrentMutationState`                 | —                                                                        |
| `status$`         | —                                                      | `ReadonlyMap<key, ConcurrentMutationState>`; a key with no entry is idle |
| `settled$`        | One outcome per call: `success`, `error`, or `dropped` | Same, each with `key`                                                    |
| `dismiss$`        | Clears `failures` and `lastSuccess`                    | Same, for one record                                                     |
| `dismissAll$`     | —                                                      | Same, for every record                                                   |
| `dropWaiting$`    | Drops every call that has not started                  | Same, for one record                                                     |
| `dropWaitingAll$` | —                                                      | Same, for every record                                                   |

```ts
type State = {
  isPending: boolean // running or waiting calls exist
  running: TParams[] // in start order
  waiting: TParams[] // in arrival order
  failures: { params: TParams; error: unknown; settledAt: number }[]
  lastSuccess: { params: TParams; data: TData; settledAt: number } | null
}
```

- **Policies.** Under `serial` and `coalesce`, calls for a record that is busy wait. Under `coalesce`, only the newest
  waiting params are kept, and the replaced call ends as `dropped`. Pass `merge(waiting, next)` to combine partial
  updates instead; merged inputs share one call and one outcome. `key` works with every policy; under `parallel` it only
  splits state per record.
- **Failures stay until dismissed.** A later success for the same record does not clear them, because it may not cover
  what the failed call sent. `lastSuccess` is the last call to finish successfully.
- **Dismiss** only once the failures have been surfaced or retried, and the query data is at least as new as
  `lastSuccess`. Dismissing earlier makes an optimistic overlay fall back to older data until the refetch lands.
- **`dropWaiting$`** drops calls that have not been sent; each ends as `dropped`, with no callback. Calls already
  running complete and report.

### Optimistic overlay

Show the value the user asked for until the server's data catches up. The recipe is for **full values**: each call
carries the whole value of its record. For partial updates, key per field, for example `` `${id}:theme` ``, and send that
field's full value. It does not apply to `merge`d patches.

Precondition: refetch or invalidate the query in `onSuccess`, as `saveDone` does above. `Query` aborts the previous
fetch when a new one starts, so the refetch started after the save is the one that lands.

```ts
export function overlayDone(
  state: ConcurrentMutationState<Task, Task, number> | undefined,
  query: QueryResult<Task[]>,
  task: Task
): boolean {
  // 1. A call is running or waiting: show the newest params.
  const newest = state?.waiting.at(-1) ?? state?.running.at(-1)
  if (newest !== undefined) {
    return newest.done
  }
  // 2. The last success is at least as new as the query data (both use Date.now(), so ties count).
  const last = state?.lastSuccess
  if (last !== undefined && last !== null && (query.dataUpdatedAt === null || last.settledAt >= query.dataUpdatedAt)) {
    return last.params.done
  }
  // 3. Otherwise, the query data.
  return task.done
}
```

A toggle derives its next value from the overlay, not from the query data, so a quick double click sends `on` and then
`off`:

```tsx
function DoneCheckbox({ task }: { task: Task }) {
  const status = useCellValue(saveDone.status$)
  const query = useCellValue(tasksQuery.data$)
  const save = usePublisher(saveDone.mutate$)
  const done = overlayDone(status.get(task.id), query, task)
  return <input type="checkbox" checked={done} onChange={() => save({ ...task, done: !done })} />
}
```

## Execution rules

These apply to both primitives, and matter when subscribers or callbacks publish back:

- **Order.** Each update publishes the state node first, then `settled$`, then calls the callback. A `settled$`
  subscriber reads the new state.
- **Re-entrancy.** A command published from a subscriber or callback of the same primitive runs after the current update,
  so `getValue` right after publishing does not show it yet. From anywhere else, the update is complete when `pub`
  returns. A `mutate$` from a `settled$` subscriber or callback can start a new call for the same record, which is how
  "on error, retry once" works.
- **Errors.** A throwing subscriber cannot stop the state update, `settled$`, the callback, or later updates. The first
  error is rethrown to the caller of `pub`; when a Promise settles, it surfaces as an unhandled rejection, which Node and
  vitest treat as a failure, so keep subscribers from throwing in SSR and tests. Throwing callbacks are logged with
  `console.error`. A `key` or `merge` that throws, or an invalid key, is a programming error: it is rethrown and the input
  has no outcome. Other subscribers of the same node can still miss an emission when one throws, as with any engine node.
- **Disposal.** Disposing the engine aborts running calls; nothing is reported afterwards.
- **Child engines.** A primitive's state lives in the engine that first uses it, and is shared with that engine's
  children. If a child engine uses a primitive before its parent does, the parent gets a second instance and calls can
  run twice; that setup is unsupported, and development builds warn about it. Register shared primitives in the root
  engine at startup, for example `root.register(deleteTask.mutate$)`.

## Wiring patterns

**Mutations trigger refetches in the graph, not in components.** Do it in `onSuccess`, as the examples above do. For
convenience, a link from `settled$` also works:

```ts
e.link(
  e.pipe(
    e.merge(createTask.settled$, deleteTask.settled$),
    e.filter((outcome) => outcome.type === 'success'),
    e.map(() => undefined, false) // distinct=false: consecutive outcomes must each fire
  ),
  tasksQuery.refetch$
)
```

**Routes drive query params.** A route node emits its params when matched; pipe it into `params$`:

```ts
e.link(
  e.pipe(
    tasks$, // Route('/lists/{id:string}', TasksPage)
    e.filter((params) => params !== null),
    e.map((params) => ({ listId: params.id }))
  ),
  tasksQuery.params$
)
```

Navigation then transparently refetches — no effect hooks, no param threading through components.

**Dependent queries** gate on their prerequisite:

```ts
e.link(
  e.pipe(
    userQuery.data$,
    e.map((r) => r.type === 'success')
  ),
  ordersQuery.enabled$
)
```

## Rendering results

Branch on the discriminated union:

```tsx
function TaskListView() {
  const result = useCellValue(tasksQuery.data$)

  if (result.isLoading) return <Spinner />
  if (result.isError) return <ErrorView error={result.error} />
  return <TaskList tasks={result.data} refreshing={result.isFetching} />
}
```
