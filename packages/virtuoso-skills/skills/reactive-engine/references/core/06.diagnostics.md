---
title: Propagation Diagnostics
description: Observe structured engine propagation without retaining application state or changing graph behavior.
---

## Attach an observer

`Engine.observeDiagnostics` activates structured diagnostics for one engine. It returns an unsubscribe function and retains no history:

```ts
import { Cell, describeNode, Engine } from '@virtuoso.dev/reactive-engine-core'

const total$ = Cell(0)
const removeDescription = describeNode(total$, { label: 'cart.total' })

const engine = new Engine({}, 'checkout')
const stop = engine.observeDiagnostics((cycle) => {
  console.log(cycle.transactionId, cycle.events)
})

engine.pub(total$, 42)
stop()
removeDescription()
```

Observer registrations and options are snapshotted when a concrete non-empty cycle starts. Adding or removing an observer during propagation affects only later cycles. Disposing an engine removes its observers and engine-local diagnostic identities.

## Record model

Each `PropagationCycle` contains:

- a unique `engineInstanceId`, an engine-local `cycleId`, and a synchronous `transactionId`
- the optional public `Engine.id` as `engineLabel`
- roots presented to that engine and an `origin` of `publication`, `forwarded-to-parent`, or `forwarded-from-parent`
- ordered evaluation and prune events
- projection attempts, their source and pull nodes, accepted candidates, optional distinct-suppressed candidates, and no-candidate results
- completed or aborted status, timing, and projection, comparator, subscriber, or child-propagation error evidence

`parentCycle` is present for a public publication made synchronously while an application cycle is active. The reference follows that publication when parent ownership forwards its concrete cycle to another engine. Other forwarded cycles correlate through `transactionId` and `origin`. Later asynchronous work starts a new transaction.

Cycle records are deeply frozen before delivery. Separate observers receive separate records because their capture and redaction policies can differ. Diagnostics describe execution evidence; they are not committed-state snapshots or proof that one root alone caused a multi-input result.

## Labels and node kinds

Use `describeNode(node$, metadata)` to register a label or value summarizer. Registrations form a stack: removing a later registration restores the earlier metadata. A cleanup removes only the registration that created it.

Node identities are stable within one engine and distinguish cells, streams, triggers, and resources. A Trigger remains distinct from a Stream that emits `undefined`.

## Value safety

Values are omitted by default:

```ts
engine.observeDiagnostics(observer, { captureValues: 'none' })
```

Use `captureValues: 'summary'` for bounded JSON-safe snapshots. The built-in normalizer handles long strings and collections, circular data, `bigint`, symbols, functions, dates, maps, sets, typed arrays, accessors, and unsupported objects with explicit sentinel values. It reads ordinary object and array properties through descriptors, so getters are represented as `accessor` without being invoked. Resource values are always omitted.

JavaScript cannot identify and inspect an arbitrary `Proxy` without potentially invoking its reflection traps. Proxy failures become `uninspectable`, but effects caused by a trap before it returns or throws cannot be undone. Keep proxied application values opaque with a node summarizer when trap-free capture is required.

A node summarizer selects application-specific fields before normalization:

```ts
describeNode(session$, {
  label: 'session',
  summarize: (session) => ({ accountId: session.accountId, role: session.role }),
})
```

The summarizer is trusted consumer code and receives the live value. It must not mutate the value or cause application side effects. The engine catches summarizer errors, but it cannot prevent a summarizer from reading or changing its argument.

An observer-level redactor receives only the detached JSON-safe summary and context. Its result is normalized again:

```ts
engine.observeDiagnostics(observer, {
  captureValues: 'summary',
  redact: (value, context) => (context.node.label === 'session' ? '[redacted]' : value),
})
```

Error names and messages follow the same capture and redaction policy and are read only from data properties. With value capture disabled, local errors contain only phase and node location. A `child-propagation` error identifies the failing child engine and its cycle when that child was observed. Observer and `onObserverError` failures are swallowed so diagnostics cannot change application propagation.

The redactor applies to captured values and error text. It does not rewrite node labels or `engineLabel`. Use static non-sensitive labels and sanitize both label fields in the export adapter before records leave the process.

## Suppression and performance

`includeSuppressed` defaults to `true`. Set it to `false` to omit individual distinct-suppressed candidates while retaining the final `not-emitted` result.

When no observer is installed, the engine does not allocate diagnostic cycles, events, node identities, timestamps, or value summaries. `debug(node$, label?)` remains a separate minimal opt-in console path with its existing output and cleanup behavior.

Core does not provide retained history, replay, explanations, browser globals, async lifecycle correlation, or telemetry transport. Build those policies in a consumer over `observeDiagnostics`.

## Troubleshooting procedure

1. Add `describeNode` labels to the reported root, the expected sink, and the nodes between them. Prefer stable domain names such as `query.range` over component names.
2. Observe the smallest relevant engine. In React, use provider diagnostics when `initFn` is involved, `useEngineDiagnostics` for the nearest mounted provider, or `useRemoteEngineDiagnostics` for a separate diagnostic tool.
3. Start with `captureValues: 'none'`. Inspect `roots`, ordered `events`, `result`, `outcome`, and `error.phase` before enabling values.
4. If a node did not emit, inspect its projection attempts. `distinct-suppressed` means its comparator accepted equality; `no-candidate` means no source combination produced a value; a prune event identifies the upstream non-emission that stopped downstream work.
5. If the wrong engine is involved, compare `engineInstanceId`, `engineLabel`, `origin`, and `parentCycle`. Match synchronous parent-child work by `transactionId`; do not infer a link across timers or microtasks.
6. Enable `captureValues: 'summary'` only for the nodes needed to confirm the hypothesis. Add narrow node summarizers and an observer redactor before exporting records.
7. Reproduce once, remove the observer, and compare the trace with the graph wiring and current engine ownership. Diagnostics show execution evidence; they do not assign causality or retain the state before and after a transaction.

Common interpretations:

| Evidence                                                         | Likely cause                                                         | Check next                                                  |
| ---------------------------------------------------------------- | -------------------------------------------------------------------- | ----------------------------------------------------------- |
| Root exists, sink is absent, prune follows a source              | An intermediate node did not emit                                    | Its comparator, filter, or projection attempts              |
| `distinct-suppressed` candidate                                  | The distinct comparator treated the values as equal                  | In-place mutation, reference reuse, or comparator logic     |
| `aborted` with `projection`, `comparator`, or `subscriber` phase | Application code threw synchronously                                 | The labeled node and original error rethrown by `pub`       |
| `aborted` with `child-propagation` phase                         | A descendant engine threw while processing forwarded values          | `childEngineInstanceId` and optional `childCycle`           |
| Expected cycle is missing from a React hook                      | Publication happened before the hook committed or after it unmounted | Use provider diagnostics or verify the remote engine source |
| Same transaction appears on several engines                      | Parent-child forwarding or a nested synchronous publication          | `origin`, `parentCycle`, and `engineInstanceId`             |
| Separate transaction IDs for related work                        | The second publication crossed an async boundary                     | Add application-level correlation outside core diagnostics  |
